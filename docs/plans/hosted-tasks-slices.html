Why this order

The plan deploys in step 9a.5, after all the code. The riskiest unknowns are not in the code. They are whether SDK v2 and Claude Code agree on revision 2026-07-28, whether Anthropic has tasks turned on for your session, and whether the InstaBox HTTPS proxy passes the Authorization header and answers within the 60-second request timer. A five-second slow_echo answers all of them. S1 therefore ships the thinnest task and deploys it. Every later slice deploys the same way and re-runs the S1 checks.

The demo story is "a series runs as one task". The slices build that story in the order a viewer sees it: one model, then twelve, then the question, then the polish.

Measured on 2026-10-24

  • The machine is passwerk-demo on the free standard-medium template, with 4 vCPU, 8 GiB and 20 GiB (16 GiB usable on /). It runs Debian 13 on x86_64 with systemd as PID 1, passwordless sudo, git 2.47.3 and Node 22.23.3. GitHub and the npm registry both answer 200.
  • Docker 29.8.2 is enabled under systemd, and user is in the docker group. hello-world runs, and node:22-bookworm-slim runs with --read-only and reports v22.23.4. So S1 uses Docker with --restart unless-stopped.
  • Port 8080 is published as https://8080-<id>.instabox.tech. The real URL stays out of the repo.
  • The proxy passes Authorization, Origin and POST bodies. It adds X-Forwarded-For, X-Forwarded-Host and X-Forwarded-Proto: https. It rewrites Host to 127.0.0.1:8080. A round trip from the laptop takes 0.75 to 0.80 s over 10 calls.
  • The proxy answers 502 if the first byte takes longer than about 20 s. Responses at 10 s and 18 s came back 200, and at 22 s, 30 s and 65 s came back 502 after 20.7 to 20.9 s. Once the first byte is sent, a stream survives 25 s silences and ran for 76 s. SSE events arrive one second apart, as written, so the proxy does not buffer them.
S1

A task travels from InstaBox to Claude Code

branch feat/hosted-tasks-s1ADR D-047highest risk

A remote passwerk server answers slow_echo as an MCP task. Claude Code shows 1 MCP task, lists it in /tasks, and reports the echoed text when it completes.

Data shape first

type TaskId = string & { readonly brand: 'TaskId' }   // 'ser_' + 26 random base32 chars
type Task =
  | Base & { status: 'working' }
  | Base & { status: 'input_required'; inputRequests: Record<string, InputRequest> }
  | Base & { status: 'completed'; result: CallToolResult }
  | Base & { status: 'failed'; error: { code: number; message: string; data?: unknown } }
  | Base & { status: 'cancelled' }
type Base = { taskId: TaskId; tool: string; statusMessage?: string;
              createdAt: string; lastUpdatedAt: string; ttlMs: number | null; pollIntervalMs: number }
interface TaskStore { create; get; update; list }   // in memory now, SQLite in S5

The union makes a completed task without a result, or a failed task without an error, impossible to construct. tasks/get serialises exactly the fields of its variant.

Appendix. SDK v2 facts

Read from the extracted @modelcontextprotocol/server 2.3.1, node 2.1.1, client 2.3.1 and core 2.3.1 tarballs. Nothing from them was run.

  • 2.3.1 negotiates 2026-07-28 through server/discover. The constant is internal (FIRST_MODERN_PROTOCOL_VERSION). The public LATEST_PROTOCOL_VERSION still reads 2025-11-25, so do not test against it.
  • Stateless HTTP is createMcpHandler(factory, { legacy, responseMode, maxRequestBodySize }), which returns { fetch, close, notify, bus }. toNodeHandler adapts it to node:http. The node package pulls in hono and @hono/node-server.
  • There is no tasks helper. The plan's fallback applies. Build the extension by hand. The 2025 task API (isTaskAugmentedRequestParams) is deprecated with no runtime behind it, so the plan's pointer to it is a dead end.
  • tasks/get must return resultType: "complete", which the SDK also enforces for custom methods.
  • The SDK's input_required helpers are for same-request round trips, not task status. S4 builds inputRequests on the task itself.
  • A tool with an outputSchema turns a task result into isError. Register run_series without one.
  • All four packages want zod ^4.2.0 and Node 20 or later. passwerk pins Zod 4.5.4.
  • Not confirmed. Whether content: [] passes the result check unchanged. The S1 spike settles it.
