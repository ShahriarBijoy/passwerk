# Phase 3 design: oracle parity in CI and the sovereignty proof

Date: 2026-09-03. Status: approved by the owner in session. Branch: `feat/oracle-parity-and-sovereignty`.

This spec implements `docs/BUILD_PLAN.md` section 2.4 (the oracle row), section 1.3 (sovereignty)
and Phase 3 (section 7). Non-obvious choices are recorded as ADRs D-012 and D-013.

## 1. Goal and definition of done

Every emitted golden passport is replayed through the official Python `aas-test-engines`
oracle. The oracle verdict is diffed against passwerk's own verdict. Any mismatch fails CI.
A second gate proves that the whole test suite runs with zero network attempts.

Definition of done:

1. `pnpm oracle` emits the six golden passports as AAS JSON and AASX (12 files), runs the
   oracle on each, writes `docs/CONFORMANCE.md` and `docs/conformance-badge.json`, and exits
   non-zero on any verdict mismatch.
2. CI has an `oracle` job that runs `pnpm oracle`, uploads the emitted files and the report as
   an artefact, and fails if the committed report or badge drifts from the fresh run.
3. `packages/core/test/sovereignty.test.ts` exercises the complete public surface of `core`
   and `rules` under recording network guards and asserts zero attempts.
4. CI has a `sovereignty` job that runs `pnpm test` inside Docker with `--network none`.
5. The README carries an "AAS conformance 12/12" badge backed by the committed badge JSON that
   CI verifies.
6. `pnpm check` is green.

Out of scope: emitters for parts 2, 4, 5 and 7; AASX Package Explorer and BatteryPass-Ready
runs (Phase 8, recorded by hand in `CONFORMANCE.md`); extending the sovereignty test to MCP
tools, resources and prompts (Phase 6, when they exist).

## 2. What the oracle can and cannot check

Verified against `aas-test-engines` 1.0.3 in session:

- `check_json_file` and `check_aasx_file` check the AAS 3.0 metamodel and its constraints.
- `supported_templates()` lists only the ZVEI `ContactInformations` and `Nameplate` templates.
  It knows nothing about IDTA 02035, so it cannot check template conformance (our L3).
- `check_aasx_file` walks `[Content_Types].xml`, the origin and spec relationships, and
  dispatches the spec part by file extension. Our JSON-only package passes.
- Results are an `AasTestResult` tree with a `Level` (INFO, WARNING, ERROR, CRITICAL);
  `ok()` is true for INFO and WARNING. `to_dict()` serialises the tree.

Consequently **parity means L2 parity**: the oracle must say `ok` exactly when passwerk's L2
(aas-core verification of the emitted JSON) reports zero errors. L1 and L3 findings do not
change the expected oracle verdict. The session probe showed this holds today for all 12 files:
the three valid samples pass, `lmt-wrong-date-format` and `industrial-bad-decimal` fail on the
same element passwerk flags, and `ev-missing-material-identifier` (L3 only) passes.

## 4. emit-golden.ts

Runs with `tsx` after `pnpm build`, importing `@passwerk/core` from its built `dist`.

For each name in `VALID_SAMPLE_NAMES` then `BROKEN_SAMPLE_NAMES`:

1. `report = validate(getSample(name))`. Every golden sample yields `aasJson` today; if one
   ever does not (an L1 schema failure), the script exits 1 with the name, because a golden
   sample that cannot be emitted cannot be oracle-checked and must not silently vanish.
2. Write `out/<name>.aas.json` (the canonical string, unchanged) and `out/<name>.aasx`
   (`packAasx(aasJson)`).
3. Collect an entry per file:

```json
{
  "sample": "lmt-wrong-date-format",
  "file": "lmt-wrong-date-format.aasx",
  "format": "aasx",
  "sha256": "...",
  "passwerk": { "verdict": "invalid", "l1Errors": 1, "l2Errors": 1, "l3Errors": 0 },
  "expectedOracleOk": false,
  "l2Findings": ["/submodels/0/submodelElements/4: ..."]
}
```

`expected.json` is `{ "generatedBy": "@passwerk/core <version>", "files": [...] }` with files
sorted by name, canonical key order. `expectedOracleOk` is `l2Errors === 0`.

## 5. oracle.py

Plain Python 3.10+, standard library plus `aas_test_engines`. No other dependencies.

1. Read `out/expected.json`.
2. For each file call `check_json_file` or `check_aasx_file` (version `3.0`), capture
   `result.ok()`, `result.level.name` and the flattened list of ERROR and CRITICAL messages.
3. Write `out/results.json`: `{ oracle: { name, version }, files: [ { file, ok, level,
   errors: [...] } ] }`.
4. Compute parity per file: `ok == expectedOracleOk`. Print one line per file.
5. Write `docs/CONFORMANCE.md` and `docs/conformance-badge.json` (section 6).
6. Exit 1 if any file lacks parity or any result is CRITICAL (an internal oracle error is
   never a pass). Exit 0 otherwise. Any mismatch is a passwerk bug until proven otherwise.

The script never touches the network: `aas_test_engines` bundles its schemas.

## 6. Report and badge

`docs/CONFORMANCE.md`:

```
# AAS conformance

Generated: 2026-09-03T12:00:00Z
Oracle: aas-test-engines 1.0.3
passwerk: @passwerk/core 0.0.0
Parity: 12/12

| Sample | Format | passwerk L2 | Oracle | Parity | Oracle messages |
|---|---|---|---|---|---|
| ev-valid | json | valid | ok | yes | |
| lmt-wrong-date-format | aasx | 1 error | ERROR | yes | Value '01.03.2026' is not a 'xs:date' @ ... |

## What parity means
(fixed prose from section 2)

## Manual oracle runs
(table kept by hand; Phase 8)
```

Only the `Generated:` line changes between runs on the same commit. The CI drift check is
`diff <(grep -v '^Generated:' docs/CONFORMANCE.md) <(grep -v '^Generated:' fresh)`; the
"Manual oracle runs" section is copied verbatim from the existing file by `oracle.py` so
hand-written entries survive regeneration.

`docs/conformance-badge.json` follows the shields.io endpoint schema:

```json
{ "schemaVersion": 1, "label": "AAS conformance", "message": "12/12", "color": "brightgreen" }
```

`color` is `red` when parity is not complete. README badge:

```
![AAS conformance](https://img.shields.io/endpoint?url=https://raw.githubusercontent.com/ShahriarBijoy/passwerk/main/docs/conformance-badge.json)
```

The number is CI-backed because the `oracle` job fails when the committed JSON differs from
the fresh run.

## 7. sovereignty.test.ts

Location: `packages/core/test/`. It is a test, so `node:*` imports are allowed.

Guards, installed in `beforeAll` and removed in `afterAll`, each recording `{ api, target }`
into an `attempts` array and throwing `Error('passwerk sovereignty: network attempt')`:

- `net.Socket.prototype.connect` (catches http, https, tls, undici and any raw socket)
- `dns.lookup`, `dns.resolve`, `dns.resolve4`, `dns.resolve6`, and the same on `dns.promises`
- `tls.connect`
- `http.request`, `http.get`, `https.request`, `https.get`
- `globalThis.fetch`

Exercise, after `vi.resetModules()` and dynamic `import('@passwerk/core')` and
`import('@passwerk/rules')` so module-load side effects are under the guards too:

- rules: read `artefactManifest`, `templates`, `attributes`, `ecDataPoints`, `timeline`,
  `plausibilityRules`, `templateCatalogue`, and call `getAttribute` and `getTemplateElement`
  for every attribute id and template path.
- core: `validate`, `emitAasJson`, `emitAasx` and `readAasxEnvironment` on all six samples;
  `validateSchema`, `validateAas`, `validateTemplate` on the emitted JSON.

Assert `attempts` is empty and, as a self-check that the guards work, that a direct
`fetch('http://127.0.0.1:9/')` inside the guarded window throws and records exactly one
attempt (removed from the count before the final assertion).

`browser-safety.test.ts` additionally walks `packages/rules/src` with the same regexes.

## 8. Docker sovereignty job

`tools/sovereignty/Dockerfile`:

```
FROM node:22-bookworm-slim
RUN corepack enable
WORKDIR /app
COPY . .
RUN pnpm install --frozen-lockfile
CMD ["pnpm", "test"]
```

CI: `docker build -f tools/sovereignty/Dockerfile -t passwerk-sovereignty .` (network on,
installs dependencies), then `docker run --rm --network none passwerk-sovereignty`. The
image build honours `.dockerignore` (node_modules, dist, .git, tools/oracle/out).

## 9. CI changes

```yaml
oracle:
  name: Oracle parity (aas-test-engines)
  needs: test
  runs-on: ubuntu-latest
  steps: checkout, pnpm, node (.nvmrc), uv (astral-sh/setup-uv, version pinned),
         pnpm install --frozen-lockfile, pnpm build, pnpm oracle,
         drift check on docs/CONFORMANCE.md (minus Generated) and docs/conformance-badge.json,
         actions/upload-artifact: tools/oracle/out + docs/CONFORMANCE.md (retention 30 days)

sovereignty:
  name: Sovereignty (--network none)
  needs: test
  runs-on: ubuntu-latest
  steps: checkout, docker build, docker run --network none
```

Both jobs run on every push to `main` and every pull request. Windows and macOS do not run
the oracle; the Python side is CI-only and Linux-only by design.

## 10. Testing

- `tools/oracle/test/expected.test.ts` (vitest; `vitest.config.ts` and `tsconfig.test.json` gain
  `tools/*/test` includes): `emit-golden` logic is a pure function `buildExpected(reports)`
  covered by a unit test; the writer is a thin shell around it.
- `tools/oracle/test_oracle.py`: `pytest`-free, runs as `python -m unittest`, tests the
  parity function and the report renderer with fixture results.
- The end-to-end proof is `pnpm oracle` itself in CI.
- Existing `golden.test.ts` remains the TypeScript-side DoD for Phase 2.
